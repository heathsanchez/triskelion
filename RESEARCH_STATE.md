# Triskelion / Metalogic Research State

_Last reconciled: 2026-08-14 13:55 NZST_

## Current strongest synthesis

Triskelion is testing a **self-extending verified capability algebra** with an explicit boundary between verified developmental knowledge and neural proceduralization.

At state `A_t`, the system has verified operators/capabilities, permitted compositions, scoped laws, provenance, revision conditions, and an external verifier authority. For a target `T`, the discipline is:

`closure first -> residual/obstruction -> minimal construction -> external verification -> scoped retention -> causal reuse -> optional neural compilation -> revision/revocation`

The useful distinctions are now:

1. **Reuse** — invoke an existing verified capability.
2. **Composition** — lawfully construct a capability from existing generators.
3. **Law formation** — retain a scoped verified equivalence/composition rule.
4. **Generator formation** — add a capability absent from the frozen old closure.
5. **Discoverability growth** — retained capability changes what later obstruction can be exposed.
6. **Constructor growth** — verified instances induce a reusable constructor family.
7. **Compilation** — explicit verified capability is proceduralized into neural weights while the explicit package remains authoritative.
8. **Activation/routing** — select the applicable capability without collapsing distinctions or violating scope.
9. **Revision/revocation** — later counterevidence changes or removes the explicit capability and any procedural attachment.

The newest evidence sharply separates explicit verified knowledge from neural proceduralization. The explicit algebra can construct, transfer, ablate, revise and revoke a scoped capability. A bounded single-capability compiler can work extremely well (IKKF V1). But multi-capability selection and whole-stack scoped compilation are **not solved**: V2b, V2c and V3 all provide falsifying evidence at the neural activation/representation boundary.

## Current architecture hypothesis

The explicit architecture remains:

`CapabilityGraph / Lawbook -> dependency + scope check -> applicability/route decision -> selected capability/module -> execution -> verifier -> retain/revise/revoke`

The new constraint is that the applicability/route decision should **not be assumed to be safely learnable as an unconstrained neural reflex**. V2c kept execution modular yet the selector still collapsed to one label. V3 preserved the correct explicit package while the frozen compiler learned the wrong activation behavior: two correct-scope compilations collapsed to `NOOP`, whereas an inverted-scope control activated everywhere.

The highest-value neural question is therefore no longer simply “modular vs monolithic?” It is:

> How can explicit verified scope/applicability semantics be proceduralized or accelerated without losing the distinction that determines when a capability is allowed to fire?

A likely successor architecture keeps scope/dependency authority explicit and lets neural components propose or accelerate decisions that remain checked against the CapabilityGraph/Lawbook. This is an empirical hypothesis, not yet a general result.

## Mathematical framing

A developmental algebra can be represented approximately as

`A_t = (O_t, L_t, V, D_t, K_t, C_t, R_t)`

where:

- `O_t`: verified generators/capabilities;
- `L_t`: scoped verified laws/composition rules;
- `V`: external verifier authority;
- `D_t`: frozen discovery procedure;
- `K_t`: constructor algebra;
- `C_t`: compilation mechanism from explicit capability to procedural/neural form;
- `R_t`: routing/activation policy over available capabilities.

Useful distinctions:

- `Closure(A_t)`: what is already reachable by lawful composition.
- `Discoverable(A_t)`: what new obstruction/generator the frozen discovery process can expose.
- `Constructible(K_t)`: what capability schemas the current constructor algebra can express.
- `Compilable(C_t, O)`: whether an explicit capability can be proceduralized under a frozen compiler.
- `Selectable(R_t, O_1...O_n, x)`: whether the correct installed capability is invoked for context `x`.
- `ScopePreserving(C_t, O)`: whether proceduralization preserves the verified applicability boundary of `O`, not merely its output token/action.

IKKF V1 gives bounded positive evidence for `Compilable` on one capability/domain. V2b and V2c are negatives for the tested forms of `Selectable`. V3 is a negative for the tested whole-stack `ScopePreserving` neural compiler while simultaneously giving positive evidence for explicit scoped construction/revision.
